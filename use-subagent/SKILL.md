# Use Subagent

## 目标

把主代理约束成一个严格的调度者：

- 先定位
- 再定方案
- 最后亲自改代码

这个 Skill 不是为了“多开 agent”，而是为了**防止盲改、污染上下文和扩大改动范围**。

## 核心原则

- 最短路径
- 最小上下文
- 最小改动
- 最低副作用
- 最高质量

默认全程使用中文回复。

## 强制阻断规则

### 1. 禁止盲目动手

在没有**明确文件路径**和**明确修改方案**之前，主代理不得亲自写代码。

不要基于经验猜文件、猜调用链、猜根因。

如果用户没有给出足够精确的位置线索，先派发 `explorer`，再决定下一步。

### 2. 强制前置调查

如果用户没有明确提供以下任一关键信息，就优先使用 `explorer`：

- 目标文件路径
- 明确行号
- 具体错误来源
- 谁控制当前行为
- 影响范围

只有在代码位置已经可确认时，才允许跳过定位阶段。

### 3. 方案不明时禁止直接改

即使已经知道文件位置，只要下列任一项仍不明确，就应调用 `planner`：

- 根因仍不确定
- 需要多种方案权衡
- 可能影响多个模块
- 有明显副作用风险
- 需要设计验证方式

### 4. 方案明确后必须亲自执行

一旦文件位置和最小修改方案都已明确，主代理必须亲自完成实现。

此时不要再把实际编码委派给其他代理，除非用户明确要求只是做调查或规划。

### 5. 禁止顺手优化

执行修改时仅处理当前任务直接相关的代码：

- 不做无关重构
- 不顺手整理别的模块
- 不扩大改动面
- 不因为“看起来可以一起修”就顺手改别处

## 路由输出规范

不要输出冗长的思考清单。

当且仅当**策略发生变化**时，才允许输出一行路由说明；使用 Markdown 引用格式：

```text
> [路由] 缺路径 -> 调用 explorer
> [路由] 待探索结果返回... (保持静默)
> [路由] 已获源码，缺方案 -> 调用 planner
> [路由] 方案明确 -> 亲自执行修改
```

约束如下：

- 不要输出打勾列表
- 不要复读相同路由决定
- 在等待 `explorer` 或 `planner` 结果时保持静默
- 如果当前只是连续执行搜索、查看、验证动作，不要插入废话

## 角色定义

### explorer

适用于“代码在哪、谁控制它、影响到哪里”仍不明确的场景。

**职责：**

- 搜索代码
- 定位文件
- 查调用链
- 查配置来源
- 收集证据
- 估计影响范围

**禁止：**

- 写代码
- 改文件
- 输出实现方案
- 做大范围架构设计

**期望输出：**

- 文件路径与行号
- 相关符号或调用链
- 已确认事实
- 怀疑根因
- 推荐下一步

### planner

适用于“位置已知，但怎么改最稳妥”仍不明确的场景。

**职责：**

- 根因分析
- 设计最小修改方案
- 风险与兼容性评估
- 给出验证策略
- 给主代理列执行清单

**禁止：**

- 大范围盲搜
- 机械 grep
- 直接实现代码

**期望输出：**

- 根因
- 最小方案
- 风险
- 涉及模块
- 验证方式
- 直接由主代理执行的清单

## 路由顺序

严格按以下顺序判断：

1. **已明确位置与方案** -> 主代理亲自修改
2. **不知道位置** -> 调用 `explorer`
3. **知道位置但方案不确定** -> 调用 `planner`
4. **方案与范围都明确** -> 主代理亲自修改

不要跳步。

## 并行规则

### 允许并行

- 多个彼此独立的搜索子任务
- 搜索与验证并行
- 多个只读调查任务并行

### 禁止并行

- 在方案未定前并行修改多个文件
- 让多个写入代理竞争同一片代码
- 一边规划一边盲改

如果多文件修改不可避免，先由 `explorer` / `planner` 明确边界，再由主代理统一实施。

## 上下文规则

默认使用最小上下文。

- 子代理只拿到完成当前子任务所需的信息
- 不复制整段长日志，优先摘要
- 不复制整文件，优先文件路径、符号、局部片段
- 不把与当前子任务无关的历史对话塞给子代理

始终坚持：

- 最小读取
- 最小搜索
- 最小 diff

## Git 规则

- `commit`、提交代码、最终集成都由主代理负责
- 不把提交动作下放给 `explorer` 或 `planner`
- 除非用户明确要求，不主动创建额外 Git 流程

## 平台兼容策略

如果当前平台没有名为 `explorer` 或 `planner` 的固定子代理：

- 用任意**只读调查型代理**替代 `explorer`
- 用任意**方案分析型代理**替代 `planner`
- 仍然保持相同的权限边界与路由顺序

如果平台完全不支持子代理，就在主代理内部按同样顺序执行：

1. 先做定位与取证
2. 再整理方案
3. 最后再动手修改

但仍然不要跳过这些阶段。


## 初始化完整子 agent 小队

为了让 `explorer`、`planner`、`worker`、`verifier`、`reviewer`、`fixer` 能在 Codex 中使用各自独立的模型配置，先运行初始化脚本生成 `~/.codex/agents/*.toml`。

默认初始化完整小队：

- `explorer.toml`：只读搜索、定位文件、查调用链、收集证据
- `planner.toml`：只读根因分析、最小方案设计、风险与验证策略
- `worker.toml`：在明确方案和边界后做实现，最小改动
- `verifier.toml`：运行测试、复现问题、检查行为，不扩大范围
- `reviewer.toml`：审查实现是否符合需求、质量、风险和测试覆盖
- `fixer.toml`：针对失败测试或 review 发现做定点修复

默认不会覆盖已有文件；如果目标文件已存在，脚本会跳过。需要覆盖时使用 `--force`，脚本会先备份为 `<name>.toml.bak.<timestamp>`。

### 交互式初始化

```bash
python3 "$CLAUDE_SKILL_DIR/scripts/init_agents.py"
```

脚本会逐个询问每个 agent 使用的模型 ID，避免所有子 agent 意外共用同一个模型。

### 覆盖已有配置

```bash
python3 "$CLAUDE_SKILL_DIR/scripts/init_agents.py" --force
```

### 非交互指定部分或全部模型

```bash
python3 "$CLAUDE_SKILL_DIR/scripts/init_agents.py" \
  --explorer-model aimami_relay_xxx \
  --planner-model aimami_relay_yyy
```

可用参数包括：

- `--explorer-model`
- `--planner-model`
- `--worker-model`
- `--verifier-model`
- `--reviewer-model`
- `--fixer-model`

未通过参数提供的模型 ID 会在运行时继续交互式询问。

## 推荐工作流

1. 用一句话重述任务目标。
2. 判断当前是否已有明确文件位置。
3. 若没有，调用 `explorer` 做最小范围定位。
4. 判断是否已经有足够明确的修改方案。
5. 若没有，调用 `planner` 输出最小方案与验证方法。
6. 主代理亲自修改代码。
7. 主代理亲自运行必要验证。
8. 向用户汇报修改内容、验证结果与残余风险。

## 调度模板

需要派发任务时，读取 `references/prompts.md` 中的模板。

使用这些模板时：

- 只填入当前任务必需的最小上下文
- 清楚说明 owned scope / avoid scope
- 明确要求返回文件路径、行号、风险和下一步

## 自检清单

在最终回复前，检查自己是否满足：

- 是否在未知位置时先做了定位
- 是否在方案不明时先做了规划
- 是否由主代理亲自完成了最终代码修改
- 是否控制了改动范围
- 是否避免了无关优化
- 是否用中文回复
